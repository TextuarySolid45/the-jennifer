# Design: Menu Item Flavors

Generated by /office-hours on 2026-08-26
Branch: main
Repo: the-jennifer
Status: APPROVED
Mode: Builder

## Problem Statement

Menu items today are flat — a bagel is just "bagel," with no way to represent that it comes in garlic or jalapeño-cheddar, and no way for the aunt to pull a flavor off the menu (out of dough, seasonal, whatever) without deleting the whole item. Guests currently order by tapping a card once; the order line item can't distinguish "2 garlic bagels" from "1 jalapeño-cheddar bagel" because `OrderItem` only keys off `itemId`.

## What Makes This Cool

Ordering starts reflecting what she's actually baking that week — she flips one flavor off, guests instantly stop seeing it as an option, no menu-item juggling. And it stays a one-tap flow for anything that doesn't need it: a plain sourdough loaf orders exactly like it does today.

## Constraints

- Items without flavors must keep working exactly as they do today — one-tap add, no picker, no schema-required change to existing rows.
- Flavor availability is a visibility toggle, not a delete — the aunt can flip a flavor back on later. Distinct from the existing `Item.deletedAt` hard-hide pattern.
- Guest read access to flavor availability is enforced client-side (filter `available === true` in the list query), not via AppSync auth — Amplify's field/model-level authorization can gate by role, not by a row's own field value.
- Scope is flavors only. Item-level availability already exists (`deletedAt`); not touched here.
- Flavor carries a name only — no separate picture/description/price per flavor, matching the user's own framing ("a bagel item with garlic and jalapeño cheddar available").

## Premises

1. Flavor belongs to one Item; zero-flavor items are visually and behaviorally unchanged. — agreed.
2. "Not available" hides the flavor from guests entirely; the aunt still sees and can re-enable it. — agreed.
3. Guest-side hiding of unavailable flavors happens in the query/UI layer, not AppSync authorization — a real platform constraint (Amplify Gen2 has no row-value-conditional auth), not a corner cut. — agreed.
4. `OrderItem` gets an optional `flavorId`; the existing add-to-order dedupe (currently `orderId` + `itemId`) extends to also match `flavorId`, so each flavor is its own line item but repeat-adds of the same flavor still increment rather than duplicate. — agreed.
5. Out of scope: item-level availability toggle (already solved by `deletedAt`), per-flavor pricing/description/imagery. — agreed.

## Approaches Considered

### Approach A: Inline picker on the card (chosen)
A row of MUI chips appears inside `MenuItemCard` only when `item.flavors.length > 0`, filtered to available flavors; tapping a chip is what triggers add-to-order (one tap, same as today — a `Select` would need a second confirm action, which breaks the one-tap property this approach is chosen for). No-flavor items are untouched.
Effort: M (human: ~1 day / CC: ~45 min)
Risk: Low
Pros: Smallest diff — no new modal/route; reuses the card's existing click target; no-flavor items get zero extra clicks.
Cons: Gets tight past ~5 flavors on the fixed 360px card — fine for the 2-4 flavor case described.
Reuses: `MenuItemCard`, `useAddItemToOrder`'s existing dedupe-by-key pattern (extended with flavorId), `UpdateMenuItemModal`'s form patterns for flavor CRUD.

### Approach B: Dedicated "choose flavor" dialog — rejected
Separate modal for flavor selection before add-to-order. Rejected: more new UI surface (dialog, open/close state) than a 2-4-flavor bakery menu needs; only pays off if flavor lists grow long.

### Approach C: Choose flavor later, from the order side panel — rejected
Add the item first, assign flavor afterward in `OrderSidePanel`. Rejected: breaks the one-tap add flow that works today — every flavored item would need a second trip to fix up the order before it's actually correct.

## Recommended Approach

Approach A. Reuses the most existing code, ships fastest, and keeps the app's best current property (one-tap ordering) intact for anything that isn't flavored.

### Schema (amplify/data/resource.ts)

- New `Flavor` model: `name` (required string), `available` (boolean, default `true`), `itemId`/`item` (belongsTo `Item`). Same auth pattern as `Item` — guest read, aunt (`authenticated identityPool`) create/read/update/delete.
- `Item` gains `flavors: a.hasMany("Flavor", "itemId")`.
- `OrderItem` gains optional `flavorId`/`flavor` (belongsTo `Flavor`), guest create/read/update/delete (matches existing `OrderItem` auth — guests already own their own order items).

### Frontend

- `useGetItems` (or a new `useGetFlavors`) fetches flavors per item; guest-facing queries filter `available === true` client-side, aunt-facing views (management UI) show all.
- `MenuItemCard`: when `item.flavors` (available-only) is non-empty, render a compact chip row above the click target, ordered by `createdAt`; `onAddToOrder(item, flavorId)` replaces the current `onAddToOrder(item)` signature. If every flavor on an item is unavailable, the card shows a disabled "currently unavailable" state instead of silently falling back to a zero-flavor one-tap add — an item with flavors defined is never orderable with no flavor selected.
- `useAddItemToOrder`: dedupe match extends from `(orderId, itemId)` to `(orderId, itemId, flavorId)`.
- Flavor management (aunt-only): extend `UpdateMenuItemModal` with a flavor list — add/rename rows plus an availability switch per row, ordered by creation order. Reuses the existing modal rather than a new screen. Duplicate flavor names on the same item aren't validated against — same trust level as duplicate item names today, not worth guarding for a family menu. No hard-delete action in this pass (see below) — toggling availability off is how a flavor comes off the menu.
- Flavor removal is soft-delete only: Amplify Gen2 `belongsTo` has no cascade-delete, so a hard `Flavor.delete` risks an orphaned `flavorId` on historical `OrderItem` rows, or fails outright if referenced. Same discipline as `Item.deletedAt` — flipping `available: false` is the only removal path exposed in the UI; a true hard-delete (for a flavor that was never ordered, e.g. a typo) is a manual/future addition, not required for this pass.
- `OrdersAccordion` / `PastOrdersAccordion` / `OrderSidePanel`: line items show the flavor name alongside the item name where one is set (e.g. "Bagel — Garlic").

## Open Questions

- None blocking. If flavor lists ever grow past ~5 per item, revisit Approach B (dialog) — noted as a future trigger, not a current requirement.

## Success Criteria

- Aunt can add, rename, and toggle availability on flavors under an item (soft-delete only — see Frontend section).
- Guests never see an unavailable flavor in the picker; an item whose flavors are all unavailable shows as unorderable, not as a flavor-less one-tap add.
- Ordering "2 garlic bagels" and "1 jalapeño-cheddar bagel" produces two distinct `OrderItem` rows; ordering garlic twice increments one row.
- Items with no flavors order exactly as they do today — no picker, one tap.
